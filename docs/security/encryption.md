# Encryption Strategy

## Objectives and limits

Encryption protects copied profiles, backups, recordings, and powered-off
devices when the OS account or keychain is not already unlocked. It does not
protect data while Relio is actively using it from malware running as the user,
a compromised kernel, screen capture, input capture, or an attacker controlling
an unlocked session.

Relio does not design cryptographic primitives. It uses maintained,
security-reviewed libraries and versioned formats.

## Key hierarchy

```text
OS secret store
└── profile root key (random 256-bit)
    ├── database key
    ├── blob key-encryption key
    │   └── per-recording/per-segment data keys
    └── backup key-encryption key
```

Derive independent subkeys with an approved HKDF using:

- versioned domain-separation labels;
- profile ID as context;
- no user password or predictable device property.

The root key is generated by the OS cryptographic random source and stored as a
non-exported or protected secret where platform APIs permit. If a platform
secret store can hold only an opaque wrapped value, use the platform's protected
data API and store the wrapped blob beside the profile.

## Application database

The application database uses a SQLCipher-compatible SQLite build:

- raw 256-bit key supplied through the in-process database API;
- current library defaults unless a reviewed compatibility migration requires
  otherwise;
- authenticated database pages;
- encrypted journal/WAL and database temporary pages;
- memory-security features enabled where supported;
- no key in a URI, SQL string assembled for logging, command line, environment,
  config, or crash annotation.

The exact library release and cryptographic provider are pinned and recorded in
the SBOM. Community-edition attribution and license obligations must be
satisfied before distribution.

Plain SQLite is allowed only for disposable automated tests with synthetic
data. Development profiles containing real host or workspace data use
encryption.

## Recordings, logs, and large blobs

Large content uses envelope encryption outside SQLite.

- Generate a random data-encryption key for each immutable segment.
- Encrypt with a maintained streaming or chunked AEAD construction based on
  XChaCha20-Poly1305.
- Use random nonces according to the library contract; never counters shared
  across writers.
- Authenticate format version, profile ID, object ID, segment sequence, content
  type, and declared length as associated data.
- Wrap the data key with the profile's blob key-encryption key.
- Write to a protected temporary file, authenticate/finalize, fsync as required,
  then atomically rename and commit metadata.
- Treat any authentication failure as corruption/tampering and never return
  partial plaintext as valid output.

The file-format ADR must name the concrete library and test vectors before
recording implementation begins. Changing primitive or framing creates a new
format version and a resumable migration; it never mutates old ciphertext in
place without a verified replacement.

## Backups and exports

- Recovery backups are encrypted under a backup-specific key hierarchy.
- User-portable encrypted backups require a separately documented recovery
  secret and authenticated format. A normal workspace export is redacted but
  not assumed confidential merely because it excludes credentials.
- Never copy a live database file without the database backup API and integrity
  verification.
- Backup metadata identifies format, application version, schema, encryption
  version, creation time, and required recovery method without exposing
  plaintext content.

## Rotation

Root-key rotation:

1. create a new root key in the OS secret store;
2. derive new wrapping keys;
3. rekey the encrypted database into a verified replacement;
4. rewrap blob and backup data keys without rewriting large ciphertext where
   the format permits;
5. validate reads and integrity;
6. atomically switch the active key version;
7. retain the previous key only for a bounded recovery window;
8. revoke and delete it after confirmation.

Rotation is resumable and records only non-secret progress. Failure leaves the
previous profile usable.

## Lock and key-loss behavior

- When the OS secret store is locked or denied, the encrypted profile stays
  closed.
- Relio never generates a replacement key for an existing profile.
- Application lock clears active secret leases and decrypted caches but is not
  represented as protection against an attacker who controls the OS session.
- Permanent root-key loss means permanent data loss unless a separately usable
  encrypted backup exists.

## Cryptographic agility

Every encrypted object records a non-secret format and key version. Readers:

- reject unknown versions;
- do not downgrade to unauthenticated or plaintext modes;
- retain old readers only for the supported migration window;
- emit no oracle-like detail that distinguishes key guesses from tampering in a
  user-visible error.

Algorithm changes require an ADR, threat-model update, compatibility plan,
performance measurements, and independent review proportional to the change.

## Verification

Tests must inspect raw database, WAL, journal, temporary, blob, recording, and
backup files for known plaintext canaries. Also test wrong keys, nonce
uniqueness, modified headers/ciphertext, truncated writes, interrupted rotation,
rollback, cross-platform restore, and secret absence from process and diagnostic
surfaces.
